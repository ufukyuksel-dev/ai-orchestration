# Benchmark: the same agent with and without AI Orchestration

## Question

When an agent works on a repository it has worked on before, does AI Orchestration make the follow-up tasks cheaper
without making them worse?

## Setup

- **Repository:** [spring-petclinic](https://github.com/spring-projects/spring-petclinic) pinned at commit
  `a6efbed7`. The code is reset to that commit before every task, so both arms always start from the same state.
- **Task families** (`bench/tasks/holdout.json`): 2 families × 3 related tasks.
  - **H1, a read-only JSON API:** an owner with its pets, all vets with their specialties, a pet's visits.
  - **H2, CSV export:** all owners, all vets with their specialties, an owner's visits.

  Each prompt states *what* is required exactly (paths, fields, formats, ordering, status codes). The project's
  pitfalls — a `@ModelAttribute` that turns unknown ids into 500s, entities that are not the JSON shape, a formatter
  check that fails the build, a database test that needs Docker — are left for the agent to discover. The suite was
  written after the product's tuning on another suite (`final.json`, deletes and list filters). Later fixes (the
  Claude Code hooks, the learn step's "save the command that finally worked", the verify card at session start) were
  found by looking at single holdout runs, so these numbers are a development measurement, not an independent one.
- **Arms:**
  - **A:** the agent alone.
  - **B:** the same agent with AI Orchestration set up exactly like `install.sh` does, a freshly indexed project and
    no memories at the start of a family.
    - Claude Code: the prompt hook (rules and matching cards arrive with the request), the stop hook (the agent is
      asked once to save what it learned) and three MCP tools.
    - Codex: the session block in `AGENTS.md` and the MCP server (`session.bootstrap` at the start, `memory.learn` at
      the end).
- **Cumulative learning chain:** in arm B, what the agent learned in task 1 is available in task 2; tasks 1 and 2 are
  available in task 3. Memory is cleared at the start of every family and repetition.
- **Success:** hidden tests (`bench/hidden/`) plus the project's own quality gate (`./mvnw validate`) and the project's
  own test suite (without the Docker-based database tests). A task counts only if all of them pass.
- **Isolation:** each run works in a temporary git worktree outside this repository; project instruction files,
  auto-memory and web tools are disabled for both arms.
- **Metric:** total tokens the agent processed (input, cached input and output), divided by the number of successful
  tasks; for Claude Code also the dollar cost it reports. *Follow-up tasks* are tasks 2 and 3 of a family; *first
  task* is where arm B pays for learning.

## Reproduce

```bash
bench/fetch.sh && bench/server.sh start                     # isolated backend: own database and vector collections
python3 bench/run.py --suite holdout --agents claude --arms A --reps 2 --out holdout-claude-A
python3 bench/run.py --suite holdout --agents claude --arms B --reps 2 --claude-mode hook --tools lean \
        --instructions bench/instructions/v12 --out holdout-claude-B
python3 bench/run.py --suite holdout --agents codex --arms A --reps 2 --out holdout-codex-A
python3 bench/run.py --suite holdout --agents codex --arms B --reps 2 --tools lean \
        --instructions bench/instructions/v12 --out holdout-codex-B
python3 tools/bench-chart/chart.py --out docs/assets \
        --run claude:A=bench/.work/results/holdout-claude-A --run claude:B=bench/.work/results/holdout-claude-B \
        --run codex:A=bench/.work/results/holdout-codex-A   --run codex:B=bench/.work/results/holdout-codex-B \
        --note "development measurement: fixes were found on these tasks" \
        --fill README.md:BENCHMARK --fill docs/benchmark.md:RESULTS
python3 bench/calls.py --by-kind bench/.work/results/holdout-claude-B/raw/*.jsonl   # where each token went
```

Every run keeps the raw agent event streams in `bench/.work/results/<run>/raw/`.

## Limits

One repository, two task families, two repetitions per task. Agents are non-deterministic; single tasks vary by
2–3× between repetitions. The effect we measure is for follow-up work on a repository the agent has seen before; a
one-off task on an unknown repository pays the learning step and gets nothing back.
