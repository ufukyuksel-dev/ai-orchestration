# AI Orchestration: project memory and rules

A hook gives you this repository's build profile, rules, the memory cards that match your request and the files the request most likely touches (the block that starts with "AI Orchestration"). Follow those rules. Start from the profile's commands and the listed files instead of searching; when a memory card fits your task, start from its approach, files and command, and drop it if the code disagrees. More memory arrives by itself when it is useful: with the result of your first build or test (how to check here) and of a check that fails with a new error (what fixed it before). Do not look memory up on other steps; only when you are stuck (an attempt failed, or a second code search did not find what you need) or a missing project decision or convention could change the work, use `extras(op="memory.search", args={query, rootPath})`; if it returns nothing, memory has nothing for this task: do not search memory again in this task. Read independent files in one step. Check with the fastest sufficient command (one test class, then the profile's test command once); do not re-run a check that passed unless files changed since. Start the app or call it with curl only when no test can cover the requested behavior. If the `ai-orchestration` tools are missing or a call cannot connect, continue without them and do not retry.

Formatting before checks, compact check output and a final check of a changed tree are done by hooks. **Save what is worth reusing.** When you believe the whole task is done, ask what a later task in this repository would otherwise have to find out again, and save it with `memory.learn` (1-3 candidates; knowledge, not a task log or a list of changed files): the build or test command, flag or setup that finally worked after trial and error, and where things are or how they behave (the file, class or pattern to change, a pitfall) so a later task does not have to search the code for it. Call it in the same step as your final check, not as an extra step after your answer; skip it when nothing new was learned or a card you were given already says it. Also save when the user asks you to remember something. Its schema lists the fields.

**Wrong memory card.** When a card you were given is contradicted by the code, fix it in the same task without asking the user: find its id with `ai_orch memory search --query "<card topic>" --view debug` (`memoryId`), archive it with `ai_orch memory archive --memory-id <id> --reason "<why it is wrong>"` (reversible soft delete, never hard-delete), then save the corrected fact with `memory.learn`. If only tags or code locators are wrong, use `ai_orch memory update --file <request.json inside the repository>` with `memoryId`, `reason` and the corrected fields.

Saved jobs, personal memory, references and adding a rule: only when the user asks for them, through the `extras` tool; details in `skills/contracts/` next to this file. When the user asks to add a rule, save it this way, not in a file, without asking again: their request is the approval. `rules.draft`, `rules.preview`, then `rules.promote` with their request as `humanRawText`; then tell them the rule and its reach (`rule-authoring.md`).
