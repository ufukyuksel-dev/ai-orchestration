# AI Orchestration: project memory and rules

Tools come from the `ai-orchestration` MCP server. If they are missing or a call cannot connect, continue without them and do not retry.

1. **Start.** When a block starting with "AI Orchestration" is already in the conversation (from the hooks: build profile, rules, matching cards, the files the request most likely touches), it replaces this call. Otherwise, first action: `session.bootstrap(rootPath=<cwd>, task=<the user's request in one line>)`.
   - Follow the returned `rules`. If `askUser` is set, ask the user once, then call again with `loadRules` (and `remember=true` for always/never). If you cannot ask (a subagent or a non-interactive run), continue without the rules and do not call it again.
   - `pathRules` apply when you edit those paths (a directory covers everything below it). If only `pathIndex` is returned, call `rules.instructions(projectKey, scope="module", modulePaths=[<path>])` before editing a listed path.
   - `memory` cards are what an earlier task in this repo learned. Use a card whose summary fits your task: start from its approach, files and command instead of exploring, then check them against the code. Ignore cards that do not fit.
   - Call it again only after context compaction (pass `knownEtag` if you still hold the rules) or in another repository.
2. **During the task.** Start from the profile's commands and the listed files instead of searching; read only the files you need. Check with the fastest sufficient command (one test class, then the profile's test command once); do not re-run a check that passed unless files changed since. Build and test commands can take minutes: start them with `yield_time_ms: 300000` so you wait for the result once instead of polling. Start the app or call it with curl only when no test can cover the requested behavior. More memory arrives by itself when it is useful: with the result of your first build or test (how to check here) and of a check that fails with a new error (what fixed it before). Do not look memory up on other steps; only when you are stuck (an attempt failed, or a second code search did not find what you need) or a missing project decision or convention could change the work, use `memory.search(query, projectKey)` (through `extras` when it is not in your tool list); if it returns nothing, memory has nothing for this task: do not search memory again in this task. When the user asks to add a rule, save it here, not in a file, without asking again: their request is the approval. `rules.draft`, `rules.preview`, then `rules.promote` with their request as `humanRawText`; then tell them the rule and its reach (through `extras` when these are not in your tool list; `rule-authoring.md`).
3. **Save what is worth reusing, when the task is done.** With the hooks installed, formatting, compact check output and a final check of a changed tree are automatic. When you believe the whole task is done, ask what a later task in this repository would otherwise have to find out again, and save it with `memory.learn` (1-3 candidates; knowledge, not a task log or a list of changed files): the build or test command, flag or setup that finally worked after trial and error (a `procedure`), and where things are or how they behave (the file, class or pattern to change, a pitfall) so a later task does not have to search the code for it. Call it in the same step as your final check, not as an extra step after your answer; skip it when nothing new was learned or a card already says it. Also save when the user asks you to remember something. Its schema lists the fields; give `locators` as precise as you know them, e.g. `{kind:"symbol", ref:"pkg.Class#method", path:"<repo path>"}`, and use `reference: {details}` only for long-form evidence.

Details, only when needed, in `skills/contracts/` next to this file: `startup-details.md`, `memory.md`, `references.md`, `last-job.md`, `saved-jobs.md`, `personal-memory.md`, `rule-authoring.md`, `memory-delete.md`.
**Wrong memory card.** When a card you were given is contradicted by the code, fix it in the same task without asking the user: archive it (`memory.delete(memoryId, mode="archive", reason=...)`, or `ai_orch memory archive --memory-id <id> --reason "..."`; reversible soft delete, never hard-delete), then save the corrected fact with `memory.learn`. If only tags or code locators are wrong, use `memory.update` (or `ai_orch memory update --file <request.json inside the repository>`). A stale card means the code it points to is gone: repair its locators with `memory.update` (`ai_orch memory update`) or archive it, in the same task.

GitHub Copilot uses the same tools natively or through the `ai_orch` terminal command and never loads rules: `skills/copilot/session-instructions.md`.
